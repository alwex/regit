Hooks

Hooks let you plug your own logic into regit’s lifecycle — fetch a human-readable feature name from an issue tracker, generate a changelog before a release finishes, notify a chat channel, and so on.

The hooks file

regit init generates a .regit/hooks.js file at the root of your repository, listing every hook with a one-line comment. It uses CommonJS (module.exports) and is shallow-merged over regit’s defaults, so you only need to keep the hooks you care about — the others fall back to the defaults (no-ops, and the default release tag message).

The file is loaded the same way whatever your project’s package.json says: CommonJS (module.exports) works even when the project declares "type": "module", and an ES module with export default { ... } works too. .regit/hooks.cjs and .regit/hooks.mjs are also picked up. Hooks run in Node (18 or later, so fetch is available), and require resolves relative to .regit/.

Which hooks file runs

  • The file of the branch that is checked out. regit reads .regit/hooks.js from your working tree when a command starts (once per command). Branches regit creates are cut from the latest release tag, so they carry the hooks file of that tag. A hook you just committed on stable only applies when you run commands from stable (or from a branch that contains the commit) until it ships in a release.
  • Commit hook changes before running regit. The hooks file is tracked, and most commands refuse to run on a dirty tree (Current branch is dirty, cannot continue).
  • Keep secrets out of it. Read tokens and webhook URLs from environment variables (process.env.SLACK_WEBHOOK_URL): the file is committed.

Editor completion and type checking

regit-cli ships TypeScript types for hooks. Annotate the hooks object with import('regit-cli').Hooks to get completion on every context field, and — with // @ts-check or checkJs — errors when a hook misuses its context or returns the wrong type. regit-cli must be installed in the project (e.g. as a dev dependency) for the import to resolve.

Annotate a variable and export it, as above. With /** @type … */ module.exports = { … }, TypeScript only types the hook arguments and does not check what hooks return.

Every context type is exported too: FeatureStartContext, ReleaseStartContext, ReleaseAddContext, ReleaseFinishContext, ReleaseFinishedContext, PreviewStartContext, PreviewAddContext, FeaturePushContext, FeatureSummary. Every hook is optional (Hooks is a Partial):

The first argument is the feature id (f1, without feature-), the release version (1.2.0, without v) or the preview name — except getFeatureName, which receives the full branch name (feature-f1).

postPreviewAddAfter the features are merged and the preview is pushed.

When a hook fails

  • Pre hooks (preFeatureStart, preReleaseStart, preReleaseAdd, preReleaseFinish, prePreviewStart, prePreviewAdd) can stop a command: if one throws, regit aborts before creating, merging, tagging or deleting anything, prints the hook’s error and exits with code 2.
  • getTagMessage behaves like a pre hook: if it throws, or returns anything other than a non-empty string, release finish stops before pushing or merging anything.
  • Post hooks (postFeatureStart, postFeaturePush, postReleaseStart, postReleaseAdd, postReleaseFinish, postPreviewStart, postPreviewAdd) run after the git work is done. If one throws, the work is not rolled back. regit says so and names the hook, then exits with code 2 so scripts and CI still notice:

Hook context

Some hooks receive a second context argument describing what regit is about to do (pre hooks) or just did (post hooks). Hooks written with a single argument keep working.

Branch start context

Passed to preFeatureStart, postFeatureStart, preReleaseStart, postReleaseStart, prePreviewStart and postPreviewStart (types FeatureStartContext, ReleaseStartContext, PreviewStartContext). Start hooks also fire when the command only checks out an existing branch: guard “first time” automations with context.origin === 'new'.

kind'feature''feature', 'release' or 'preview'.
id'f1'Feature id, release version or preview name, without the feature- / release- / preview- prefix.
branch'feature-f1'Full branch name.
origin'new''new': the branch is created from the latest release tag. 'local': the branch already exists locally and is checked out. 'remote': the branch only exists on origin (e.g. a teammate’s feature) and is checked out for the first time.

Release tag message

release finish creates an annotated tag on stable. By default its message lists the merged feature branches:

Return your own message from getTagMessage. It receives the release version and the release finish context, and must return a non-empty string. Because it runs after preReleaseFinish, it can read anything that hook committed (e.g. a generated changelog).
